# 期货目录与历史行情同步重构交接文档

状态：原交易所快照方案已由 2026-08-24 的免费数据源验证结果取代

整理日期：2026-08-23

适用仓库：`evatick-server`，以及后续需要配套调整的 `evatick-cli`

## 0. 2026-08-24 数据源验证与实施决定

在本机和生产 ECS 上对无需 API Key 的来源做了相同日期范围的真实请求：

- 新浪 `futures_main_sina` 在 CFFEX、SHFE、INE、CZCE、DCE、GFEX 的代表
  品种上均成功，11 个交易日通常在 0.1–0.4 秒内返回。
- 新浪 `futures_zh_daily_sina` 可读取月份合约日线；郑商所目录使用三位交割
  年月，而新浪使用四位年月，适配层负责结合请求日期补全年份。
- 东方财富 `futures_hist_em` 在本机和 ECS 上均被上游主动断开，不能作为日线
  来源；`futures_hist_table_em` 仍可稳定返回六所当前合约，仅作为目录元数据。
- AKShare `get_futures_daily` 的 CFFEX 请求会超过 30 秒服务超时，DCE 匿名接口
  在 ECS 上受 WAF 限制；其余交易所即使可用，逐自然日请求也无法扩展。

因此当前实施不再按交易所日快照自行选主，而是：

1. 期货日线只把新浪声明为可用数据源，删除六个不可稳定工作的交易所日线源。
2. 每个品种用一次区间请求读取新浪未复权主力连续日线，不再逐自然日请求。
3. 同步列表只生成新浪目录明确提供主连代码的品种。
4. 当前月份合约由东方财富目录发现，行情仍直接读取新浪日线。
5. 新浪不披露连续序列每天对应的月份合约，因此成员明细为空；不得伪造换月
   归属。若未来找到可靠且免费的全合约历史快照，再恢复下文的自建连续方案。

下文保留原交易所快照方案，作为未来恢复可追溯自建连续序列时的设计参考，
不再描述当前生产实现。

## 1. 结论

当前期货同步的任务粒度不正确：系统按照“当前合约 × 整段日期”逐个请求，但 AKShare 的交易所日线接口实际上按照“交易所 × 日期范围”返回范围内所有合约。结果是同一交易所数据被每个合约重复下载，既容易超过服务端超时，也无法正确回补已经退市、但在历史日期真实存在的合约。

重构后应遵循以下边界：

1. 面向用户的期货列表默认展示**期货品种**，例如 `IF`、`AU`，避免向模型暴露大量月份合约。
2. 服务端标的目录继续保存**期货合约**，例如 `IF2501`、`AU2612`；行情柱始终归属于具体合约。
3. 全量期货历史同步按照**交易所 × 交易日**规划任务。一次取得该交易所当天全部合约的数据，发现或更新历史合约后批量写入。
4. 当前有效合约列表只能表达“现在有哪些合约”，不能充当历史同步的标的全集。
5. `IF`、`IF2501` 和 `IF 主力连续` 是三个不同对象，服务端和客户端不得静默互相替代。

## 2. 已观察到的生产现象

以下数据来自 2026-08-23 对火山云 ECS 上服务的实际检查，仅用于说明当前瓶颈，不应作为永久性能基准：

- 一次期货全量同步范围约为 `2026-05-23` 至 `2026-08-23`。
- 该次任务在最初 3 个合约均失败、写入 0 条后被取消。
- 服务端提供方请求超时为 30 秒，并配置 2 次重试。
- SHFE 合约 `ad2609` 请求 2026-08-01 至 2026-08-21：成功，15 条，约 7.10 秒。
- INE 合约 `sc2609` 同范围：成功，15 条，约 2.08 秒。
- CZCE 合约 `AP610` 同范围：成功，15 条，约 4.81 秒。
- CFFEX 合约 `IF2609` 请求 21 天：45 秒内没有完成。
- CFFEX 合约 `IC2609` 仅请求 2026-08-21：成功，1 条，约 21.20 秒。

这说明即使不考虑重复调用，较长日期范围也可能超过单次请求超时；考虑到每个合约都会重复下载交易所全量数据，当前全量同步无法扩展。

## 3. 当前实现及根因

### 3.1 提供方适配层

`providers/akshare-python/evatick_server_akshare/__main__.py` 中的 `_future_bars`：

1. 从 `providerSymbol` 解析交易所和具体合约。
2. 调用 `akshare.get_futures_daily(start_date, end_date, market=venue)`。
3. 在返回的交易所全量记录中再次过滤出目标合约。

AKShare 的该接口按日期读取交易所日线快照，其中包含当天的多个合约。因此，如果目录中有 100 个合约，现有实现会把同一批交易所数据下载约 100 次，最后每次只保留一个合约。

### 3.2 同步管理器

`packages/transport-http/src/data-sync-manager.ts` 当前统一采用逐标的任务模型：

- `DataSyncRun.total` 是标的数量。
- `sync_run_items` 的主语是 `instrument_id`。
- `execute()` 逐个标的调用 `loadBars(instrument, range)`。
- `sync_coverage` 只记录单个标的的请求范围。
- 恢复同步时重新读取当前目录，目录变化还可能产生 `DATA_SYNC_CATALOG_CHANGED`。

该模型适合股票、指数和按交易对访问的加密货币，但不适合交易所批量发布的中国期货日线数据。

### 3.3 历史语义错误

假设用户同步 `2025-01-01` 开始的数据，而当前目录是在 2026 年刷新得到：

- 2026 年当前合约在 2025 年尚未挂牌，请求结果通常为空。
- 2025 年已经到期的合约可能不在 2026 年当前列表中，因此永远不会被同步。
- 空结果不能区分“该合约当时不存在”“休市”“提供方缺数”和“请求失败”。
- 即使所有请求都成功，最终数据集仍可能系统性遗漏历史合约。

所以历史同步的合约全集必须来自各交易日的**期货挂牌快照**，不能来自今天的合约列表。

## 4. 领域模型

### 4.1 期货品种

期货品种是交易所定义的合约族，例如：

- CFFEX 的 `IF`：沪深 300 股指期货。
- SHFE 的 `AU`：黄金期货。

品种用于浏览、搜索、选择同步范围和组织合约，但它本身不是某个月份的可交易合约，也没有唯一的一条原始日线。

### 4.2 期货合约

期货合约是具体可交易标的，例如 `IF2501`。至少应维护：

- 规范标的 ID、交易所代码、合约代码。
- 所属期货品种。
- 交割月份。
- 首次交易日、最后交易日（可从权威元数据获得时）。
- 首次发现日、最后发现日（从挂牌快照观察所得）。
- 状态：未上市、活跃、到期或未知。

到期合约必须保留稳定身份，不得因为当前列表不再返回而删除。

### 4.3 期货连续序列

主力连续、指数连续等属于合成序列，必须记录换月选择和复权/价差处理规则。它不是期货品种，也不是具体合约。本轮重构可以先不生成连续序列，但接口和命令不得把品种代码静默解析成连续序列。

### 4.4 期货挂牌快照

期货挂牌快照表示某交易所在某交易日返回的全部实际挂牌合约。它既是历史合约发现来源，也是全量同步的自然任务分区。

## 5. 目标用户体验

命令名称可在实现时结合现有 CLI 约定确定，但语义应保持如下清晰分层：

```text
eva futures list
```

默认只列期货品种，可按交易所搜索或过滤。

```text
eva futures contracts --product IF --as-of 2025-01-02
```

列出指定日期实际有效或被观察到挂牌的月份合约。支持显式选择 `active`、`expired` 或 `all`，但默认输出不应把所有历史月份合约铺开。

```text
eva futures bars --contract IF2501 --start 2025-01-01 --end 2025-01-31
```

读取具体合约行情柱。如果请求范围与已知合约生命周期没有交集，应明确返回空数据及原因，不应向提供方发起无意义请求。

```text
eva futures bars --product IF --series main --start ... --end ...
```

只有显式给出 `--series` 及对应规则时才能读取连续序列。单独请求 `IF` 的行情应返回歧义/缺少参数错误，不能默认映射到当前主力合约。

```text
eva futures sync --exchange CFFEX --start 2025-01-01 --end 2025-12-31
```

全量历史回补默认选择交易所和日期范围，不要求用户提供当前月份合约列表。

## 6. 目标同步架构

### 6.1 任务规划

期货日线全量同步采用下列流程：

```text
日期范围
  -> 交易日历过滤
  -> 生成“交易所 × 交易日”分区
  -> 每个分区只请求一次交易所日线快照
  -> 规范化并识别快照中的全部合约
  -> 更新品种/合约目录及生命周期观察值
  -> 批量写入全部合约行情柱
  -> 标记分区覆盖与运行进度
```

股票、指数、加密货币等资产可以继续使用逐标的同步；不要为了统一代码形式而强迫所有资产使用同一种任务粒度。

### 6.2 提供方契约

需要为期货日线增加批量能力，概念上类似：

```ts
loadFuturesDailySnapshot({ venue, tradingDate })
```

返回值至少包括：

- 交易所和交易日。
- 上游来源。
- 当天所有合约及其 OHLCV/成交额字段。
- 必要的原始合约标识，供目录映射和问题追踪。

不能通过循环调用现有 `loadBars(instrument, range)` 来模拟该能力，否则重复下载问题仍然存在。

如果某个数据提供方原生支持高效日期范围批量请求，也可以按“交易所 × 有界日期块”请求，但持久化进度和重试仍应细化到单个交易日，避免长范围失败后全部重做。

### 6.3 合约发现与目录更新

处理每个快照时：

1. 从交易所和合约代码识别期货品种、交割月份和规范合约 ID。
2. 已存在合约只更新映射、观察日期和能力。
3. 未存在合约创建历史目录记录，即使它已经到期。
4. 不在当前快照出现不能直接判定为到期；到期状态应结合最后交易日元数据或连续多日观察规则。
5. 同交易代码跨 SHFE/INE 等场景必须保留交易所身份，不能仅按大小写代码合并。

### 6.4 写入和幂等性

- 每个交易所日分区应使用批量暂存表和集合式 upsert，避免逐行 DuckDB 写入。
- 同一分区重复执行必须得到相同结果。
- 目录更新、行情写入和覆盖标记应具有一致性；行情未完整写入时不得把分区标记为成功。
- 空快照必须保存原因或状态，例如休市、确认无挂牌、提供方空响应；不能无条件视作完整覆盖。

### 6.5 覆盖、恢复和重试

新增期货分区覆盖，主键至少包含：

```text
provider + venue + trading_date + interval
```

覆盖状态建议区分 `pending`、`complete`、`empty-confirmed` 和 `failed`。期货全量运行的进度、失败项、取消与恢复也以分区为单位，而不是以当前合约为单位。

单合约覆盖仍然可以从已写入行情柱和挂牌快照推导或单独维护，供本地行情读取使用；它不能替代交易所日分区覆盖。

### 6.6 并发和性能边界

- 先串行验证每个交易所的正确性，再对不同日期做有界并发。
- 每个交易所应拥有独立并发上限；CFFEX 当前单日约 21 秒，不适合高并发压测。
- 重试只重试失败分区，并采用退避和抖动。
- 复用同一分区结果，绝不能因目标合约数增加而增加上游请求次数。
- DuckDB 保持单写入协调器，多个抓取任务完成后进入有界批量写入队列。

目标复杂度应从近似：

```text
当前合约数 × 日期范围请求成本
```

降为：

```text
交易所数 × 交易日数
```

## 7. 服务端与客户端接口建议

### 7.1 服务端

建议在不破坏现有规范标的接口的前提下增加期货专用的发现视图：

- 期货品种列表。
- 按品种、交易所、日期和状态查询合约。
- 按交易所和日期范围启动期货批量同步。
- 查询交易所日分区覆盖、失败项和重试状态。

现有 `/v1/instruments` 仍可返回真实期货合约，以保持“金融标的目录”的语义和兼容性；管理后台和 CLI 的默认期货列表改为品种聚合视图即可。不要把品种伪装成现有合约 `instrument_id`。

### 7.2 管理后台

期货全量同步表单应优先提供：

- 交易所选择。
- 日期范围。
- 跳过已完整覆盖分区。
- 分区并发或安全预设。

运行进度展示“已完成交易所日分区 / 总分区”，失败详情展示交易所、日期、提供方和错误。合约级浏览可以继续存在，但不再用合约数量表示全量同步进度。

### 7.3 CLI

客户端命令应把 `product`、`contract`、`series` 作为不同参数名，避免统一叫 `symbol`。帮助文本至少提供一个品种、一个具体合约和一个连续序列示例，并明确连续序列需要显式规则。

## 8. 测试计划

### 8.1 单元测试

- 从 SHFE、INE、DCE、CZCE、CFFEX、GFEX 的代表性合约代码正确解析品种和交割月份。
- 大小写及跨交易所同名代码不会产生错误合并。
- 期货品种列表不会重复，也不会被当作可交易合约。
- 指定合约请求范围会与生命周期求交集；无交集时不调用上游。
- 连续序列必须显式给出规则，单独品种代码不会被静默解析。
- 重跑同一交易所日分区不会产生重复行情柱。

### 8.2 提供方契约测试

- 一个交易所日快照返回多个合约并全部保留，不在适配层过滤成单一合约。
- 日期格式对每个交易所都正确。
- 期权记录不得混入期货目录。
- 上游空响应、超时、部分字段缺失和非法数值具有明确结果。
- 测试夹具验证来源、交易所、合约 ID、OHLCV 和交易日。

### 8.3 同步集成测试

构造 2 个交易日、同交易所 3 个合约的夹具，必须验证：

- 上游只被调用 2 次，而不是 6 次。
- 三个合约都被发现并写入目录。
- 已到期且不在当前目录中的历史合约仍被创建和保存。
- 未来尚未挂牌合约不会制造虚假空覆盖。
- 第二天失败后可以只重试第二天。
- 取消并恢复时不依赖当前目录保持完全不变。
- 分区写入失败不会留下 `complete` 覆盖状态。

### 8.4 端到端与线上冒烟

开发完成后至少验证：

- 每个交易所选择一个实际交易日，同步后随机抽查多个合约日线。
- 与交易所源数据核对开高低收、成交量及合约身份。
- 跨越合约到期和新合约上市的日期范围，确认目录生命周期变化正确。
- 对相同日期范围重复同步，确认上游请求、写入数量和数据库体积受控。
- 在客户端执行品种列表、合约列表、具体合约行情和全量同步命令。
- 进行冷缓存和热缓存性能测试，记录分交易所耗时、请求次数、失败率和写入吞吐。

线上测试应使用小日期范围逐步放大，避免直接对 CFFEX 发起高并发长范围请求。

## 9. 验收标准

实现完成必须同时满足：

1. 同一交易所同一交易日的上游全量日线最多请求一次，不随合约数增长。
2. 同步历史日期时能发现并保存当时挂牌、现在已经到期的合约。
3. 未来合约不会被错误地拿去请求其挂牌前数据。
4. 默认期货列表展示品种；具体合约可以按品种、日期和状态查询。
5. 具体合约、期货品种和连续序列在 API 与 CLI 中不存在静默歧义。
6. 失败、取消、恢复和重试以交易所日分区工作，并保留可诊断错误。
7. 所有支持交易所均有自动化契约测试和至少一次真实数据冒烟结果。
8. 性能报告包含上游调用次数；性能提升不能只以客户端响应缓存命中衡量。
9. 现有股票、指数和加密货币同步行为不发生回归。

## 10. 建议开发顺序和 Commit 边界

每个独立问题保留单独 Commit，建议按以下顺序推进：

1. `docs/domain: define futures products, contracts and listing snapshots`
2. `feat: expose exchange daily futures snapshots from provider`
3. `feat: persist futures products and historical contract lifecycle`
4. `feat: sync futures by exchange trading-day partitions`
5. `feat: resume and retry futures sync partitions`
6. `feat: expose futures product and dated contract discovery APIs`
7. `feat: simplify futures admin sync workflow`
8. `feat(cli): separate futures products, contracts and series commands`
9. `test: add futures exchange correctness and performance coverage`

每个 Commit 前检查工作区和 staged diff，不得混入部署配置、凭据或其他未提交改动。

## 11. 不在首轮重构中强制完成的内容

- 主力连续、指数连续等合成算法可以后置；首轮只需确保领域和接口不产生错误映射。
- 分钟级期货行情不应复用日线批量方案冒充支持。
- 不要求一次回补所有年份；先保证任务可恢复、可观测和幂等，再逐步扩大范围。
- 不应为了该问题重写股票、指数或加密货币的同步任务模型。

## 12. 新会话启动提示

新会话可以直接使用以下目标开始：

> 阅读 `CONTEXT.md`、`AGENTS.md` 和 `docs/futures-historical-sync-redesign.md`，严格按测试驱动方式重构期货目录与日线同步。默认期货列表展示品种，历史行情按交易所与交易日批量获取并发现实际合约；不得依赖当前合约列表回补历史。逐个问题修改、测试并分别提交 Commit。完成本地测试后，再在火山云 ECS 以小范围逐交易所冒烟并汇总性能数据。
